## 1. Назначение и границы

Самостоятельный сервис для домашнего медиасервера: скачивает медиа с произвольных
платформ через внешний `yt-dlp`, складывает файлы в локальный каталог (целевое
потребление — Jellyfin) и предоставляет два интерфейса управления — веб (HTMX) и
Telegram-бот.

Ограничения по дизайну:

- один экземпляр приложения (SQLite), горизонтального масштабирования нет;
- нагрузка домашняя: единицы пользователей, тысячи файлов;
- все внешние вызовы (yt-dlp, Telegram) умеют ходить через HTTP/SOCKS5 прокси.

Внешние зависимости в рантайме: бинарь `yt-dlp`, бинарь `ffmpeg`.

## 3. Структура пакетов

Слои: **адаптеры** (HTTP, Telegram) → **сервисы** (доменные правила) →
**репозитории** (SQLite) и **исполнители** (загрузки, фоновые операции).
Зависимости однонаправлены; сервисы не знают ни об HTTP, ни о Telegram.

  queue/service.go        ДОМЕН: очередь — постановка ссылки, отмена, повтор, redownload

  api/server.go           маршруты, авторизация, SSE, монтирование по BASE_PATH

`yt_dlp_timeout`, `lib_page_size`. Собираются в одном месте —
`settings.Provider`, который кеширует таблицу и сбрасывает кеш при записи.
Пустое значение в форме удаляет ключ и возвращает env-значение.

### 4.2 Хранилище

**Пулы соединений.** Запись идёт через единственное соединение (SQLite допускает
одного писателя), чтение — через отдельный пул с `query_only`. Метод определяет
пул: `Query*` — чтение, `Exec`/`BeginTx` — запись, `WriteRowContext` — для
`UPDATE … RETURNING`. Для in-memory базы пул один.

Параметры задаются через `_pragma` (синтаксис `modernc`): `journal_mode(WAL)`,
`busy_timeout(5000)`, `foreign_keys(on)`. Внешние ключи включены, поэтому удаление
задания каскадно уносит его `items` и `job_tags`.

Миграции применяются при старте, идемпотентно, с журналом в `schema_migrations`.
Миграция 012 — разрушающая: `files` + `audio_files` объединены в `items`.

**`jobs`** — задание на скачивание: `id`, `url` (`"local"` для импорта с диска),
`status`, `title`, `error`, `source` (`web`/`telegram`/`filesystem`), `chat_id`,
`tg_message_id`, `retry_count`, `next_retry_at`, `first_failed_at`, `hidden`,
`last_log`, `created_at`, `updated_at`.

Статусы: `checking` (проверка «плейлист?») → `pending` → `running` →
`done` | `retrying` → `failed` | `cancelled`; `imported` — найдено сканером.

**`items`** — медиафайл (1 job → N items): `id`, `job_id`, `kind`
(`video`/`audio`), `path` (UNIQUE), `name`, `size`, `duration`, ID3-поля,
`created_at`, `deleted_at` (soft delete), `lost_at` (файл пропал).

**`tags`** (`kind` = `plain`|`collection`) + **`job_tags`**; **`collections`** —
коллекция реализована как тег с совпадающим именем. **`operations`** — фоновые
операции. **`tokens`** — постоянные ссылки. **`cookies`**, **`settings`**.

### 4.3 Сервисный слой

Доменные правила собраны в двух сервисах; HTTP и Telegram — их адаптеры.

**`library.Service`** — медиатека: выдача страницы (`Media`), облако тегов,
серверный плейлист, потоковая отдача и постоянные ссылки, мягкое удаление,
переименование, скрытие и безвозвратное удаление заданий, теги, коллекции,
постановка и отмена фоновых операций.

**`queue.Service`** — очередь: `Prepare` (создать заготовку), `Resolve`
(асинхронно развернуть), `Add` = оба шага, `Cancel`, `CancelAll`, `Retry`,
`Redownload`, `RecoverChecking`. Через `ExpandObserver` сообщает подписчику
(боту), чем закончилось разворачивание.

### 4.4 HTTP API

Пути указаны без `BASE_PATH`.

**Страницы:** `GET /`, `GET /settings`, `GET /login` (если задан `WEB_TOKEN`),
`GET /health`, `GET /static/…`, `GET /events` (SSE).

**Медиатека:** `GET /library/items` (параметры `q`, `kind`, `tag`, `offset`,
`rows=1` — только строки следующей страницы), `GET /library/tags`,
`GET /library/sidebar`, `GET /library/playlist` (JSON).

**Элементы:** `GET /items/{id}/stream[?download=true]`, `DELETE /items/{id}`,
`PATCH /items/{id}`, `PATCH /items/{id}/meta`, `POST /items/meta-bulk`,
`POST /items/{id}/link` (создать), `DELETE /items/{id}/link` (отозвать),
`POST /items/{id}/extract-audio` (один файл), `POST /items/extract-audio-bulk`
(набор выделенных), `GET /items/deleted`.

**Задания:** `POST /queue`, `DELETE /queue/{id}`, `POST /queue/cancel-all`,
`GET /queue/items`, `POST /jobs/{id}/retry`, `POST /jobs/{id}/redownload`,
`POST /jobs/{id}/hide` · `/unhide`, `DELETE /jobs/{id}` (только скрытые),
`POST|DELETE /jobs/{id}/tags[/{tag}]`, `GET /jobs/{id}/log`,
`POST /media/bulk-tag` · `/media/bulk-hide`.

**Операции:** `DELETE /operations/{id}` (убрать завершённую),
`POST /operations/{id}/cancel` (прервать выполняющуюся).

**Коллекции:** `GET /collections` (JSON), `POST /collections`,
`PATCH|DELETE /collections/{id}`, `POST /collections/{id}/jobs`.

**Настройки:** `POST /settings/runtime`, `POST /settings/cookies/import`,
`DELETE /settings/cookies/{domain}`, `POST /settings/reindex`, `POST /settings/cleanup`.

**Публичный:** `GET /f/{token}[?download=true]` — файл по постоянной ссылке
в обход авторизации; удалённые и потерянные элементы отдают `410`.

### 4.5 Авторизация

При заданном `WEB_TOKEN` доступ требует либо заголовка
`Authorization: Bearer <token>`, либо cookie `_auth`. Cookie выставляет форма
входа `GET|POST /login` (`HttpOnly`, `SameSite=Lax`, `Secure` за HTTPS).
Без авторизации доступны: `/login`, `/static/…`, `/f/…` и health-эндпоинт.
Навигационные GET-запросы редиректятся на форму входа, остальные получают `401`.

### 4.6 Загрузка (worker.Pool)

- `WORKER_COUNT` горутин; пробуждение по сигналу или таймеру раз в 10 с.
- `ClaimNext` — атомарный `UPDATE … RETURNING`: берёт старейший `pending` либо
  `retrying` с наступившим `next_retry_at`.
- На старте `ResetStale` возвращает зависшие `running` в `pending`; задания в
  `checking` не трогаются — их заново разворачивает `queue.RecoverChecking`.
- Загрузка идёт в `StagingDir()/<jobID>`; каждый готовый файл переносится в
  медиатеку (`os.Rename`, fallback на копирование), регистрируется в БД, и по нему
  сразу уходит событие в UI и карточка в Telegram.
- Ошибка фатальна, только если не скачан ни один файл (частичный успех плейлиста — успех).
- Отмена: `context.CancelFunc` на задание; `CancelJob` убивает процесс.

**Backoff:** `delay = RETRY_BACKOFF_BASE << (retry_count-1)` (сдвиг ≤ 15).
Если `now + delay` выходит за `first_failed_at + RETRY_MAX_DURATION` — `failed`.

### 4.7 Разворачивание ссылок

`Prepare` создаёт задание в статусе `checking` (воркер его игнорирует) и сразу
возвращает управление. `Resolve` в горутине запускает
`yt-dlp --flat-playlist --simulate`:

- 0–1 записей или ошибка → `checking` → `pending`;
- ≥2 записей → заготовка удаляется, создаётся по заданию на видео, все помечаются
  тегом с названием плейлиста.

Результат уходит наблюдателю (`ExpandObserver`), поэтому Telegram-бот может
заменить сообщение «в очереди» сводкой по плейлисту. Таймаут проверки — 45 с.

### 4.8 Фоновые операции (ops.Worker)

Две независимые полосы; внутри полосы операции идут по одной:

| Полоса | Виды | Почему |
|---|---|---|
| `light` | `bulk_tag`, `bulk_hide` | только запись в БД, завершаются мгновенно |
| `heavy` | `bulk_meta`, `update_meta`, `extract_audio`, `reindex`, `cleanup` | ffmpeg или обход диска |

Каждая операция исполняется под контекстом с таймаутом `OPS_TIMEOUT` и может быть
прервана (`POST /operations/{id}/cancel`). При старте `ResetStale` возвращает в
очередь операции, оборванные рестартом. Виды с `ShowInQueue=false` (`reindex`,
`cleanup`) удаляются из таблицы сразу после выполнения; остальные завершённые
записи подчищаются раз в час по сроку `OPS_RETENTION_HOURS`.

### 4.9 Извлечение аудио

Операция принимает набор файлов: из меню строки приходит один, из панели
массовых действий — все выделенные видео. Повторы и недоступные файлы
отсеиваются до постановки в очередь, ошибка на одном файле не отменяет
остальные — частичный успех считается успехом, подробности уходят в лог.

Теги дорожки берутся из названия исходного видео, источник скачивания в них не
попадает (раньше в «исполнителя» записывался домен, и вся музыка оказывалась
«от youtube.com»). Разбор в `audio.ParseTitle`: убираются расширение, артефакты
yt-dlp и служебные пометки вроде `(Official Video)`, затем название делится по
тире (`Исполнитель - Композиция`) либо по русской записи `Исполнитель «Название»`.
Если разделить не удалось, исполнитель остаётся пустым, а название целиком идёт
в «композицию» — выдумывать исполнителя хуже, чем оставить поле пустым.

После извлечения задание помечается тегом `аудио`: по нему в медиатеке одним
кликом видно, из чего дорожку уже доставали.

### 4.10 Фоновые сканеры

- **FileChecker** (`FILE_CHECK_INTERVAL`) — периодическая сверка записей с диском.
- **DirScanner** (`DIR_SCAN_INTERVAL`, по умолчанию выключен) — импорт файлов,
  появившихся на диске: пропускает dot-каталоги, `.part`/`.ytdl`, неизвестные
  расширения, уже известные пути и пути «в полёте».

Сама сверка живёт в пакете `filecheck` и используется и сканером, и `reindex`.

### 4.11 Реал-тайм (SSE)

`sse.Hub` рассылает не общий сигнал, а конкретные темы: `library`, `queue`,
`tags`, `collections`. Публикации склеиваются в окне 300 мс — при разворачивании
плейлиста из полусотни видео вкладка получает несколько обновлений вместо
полусотни полных перерисовок списка.

Эндпоинт `/events` отдаёт каждую тему отдельным именованным SSE-событием;
браузер переводит их в HTMX-события (`mediaRefresh`, `queueRefresh`,
`tagsRefresh`, `collectionsRefresh`) и обновляет только затронутый фрагмент.
Темы публикуют: пул загрузок (очередь + медиатека), исполнитель операций
(набор зависит от вида операции), разворачивание ссылки и сервис очереди.

### 4.12 Telegram-бот

Long polling, каждое обновление в своей горутине. Доступ — по
`TELEGRAM_ALLOWED_IDS` (пустой список пускает всех).

Команды: `/start`, `/help`, `/status`, `/queue`, `/last [N]` (≤20),
`/search <запрос>` (по имени, URL, заголовку и тегам), `/web`.

Сообщение со ссылками разбивается по пробелам; каждая ссылка ставится в очередь
**без ожидания** yt-dlp. Жизненный цикл сообщения: `В очереди` → `Скачивается…` →
карточка на каждый файл → сообщение очереди удаляется. Если ссылка оказалась
плейлистом, сообщение заменяется сводкой. При ошибке — кнопка «Повторить».

Кнопки: при публичном `BASE_URL` — прямые URL-кнопки, иначе callback-кнопки
с отправкой ссылки текстом.

## 5. Фронтенд

### 5.1 Архитектура

Серверный рендеринг templ + HTMX для обновления фрагментов + нативные ES-модули
для состояния плеера, выделения и диалогов. Сборщика нет: браузер грузит модули
сам. `<base href="{BASE_PATH}/">` делает относительные URL корректными за Ingress.

```
web/static/
  app.css              оформление целиком (тёмная тема на CSS-переменных)
  js/
    main.js            точка входа: собирает модули, подписка на SSE
    actions.js         делегирование событий по data-action
    api.js             запросы, разбор HX-Trigger, экранирование
    toast.js           уведомления
    filters.js         раздел, тип, коллекция, поиск, облако тегов
    player.js          видео и аудио, очередь воспроизведения, нижняя панель
    selection.js       выделение строк, панель действий, диалог ID3-тегов
    collections.js     выпадающий список и управление коллекциями
    library.js         действия над строкой: ссылки, переименование, удаление, лог
    menu.js            меню строк, поведение диалогов
```

**Делегирование событий.** Разметка объявляет намерение
(`data-action="row-play"`, `data-action-change="row-select"`,
`data-action-input="search"`), модули регистрируют обработчики. Единый слушатель
на `document` переживает подмену фрагментов HTMX — навешивать обработчики заново
не нужно. Inline-обработчиков (`onclick=`) в шаблонах нет: именно из-за них
переименование функции молча превращало кнопку в неработающую.

Согласованность половин проверяется тестом `web/templates`: он рендерит все
компоненты, собирает использованные действия и сверяет их с зарегистрированными
в JS. В браузере то же самое делает `auditActions()` — при загрузке и после
каждой подмены фрагмента.

Запросы из JS идут через обёртку `api()`, которая читает заголовок `HX-Trigger`
и рассылает те же события, что и запросы HTMX, — механизм обновления UI один.

### 5.2 Структура главной страницы

- **Шапка**: логотип, форма добавления ссылки, кнопка настроек.
- **Сайдбар**: «Очередь», фильтры «Все / Видео / Аудио», коллекции со счётчиками
  и меню действий (переименовать, удалить). На мобильном — горизонтальная полоса чипов.
- **Панель инструментов**: поиск, облако тегов (первые 5 + «ещё N»), «выбрать все».
- **Список медиа**: строки с чекбоксом, иконкой, названием, доменом, размером,
  чипом статуса, тегами и меню действий; в конце — кнопка «Показать ещё» с
  счётчиком «N из M», подгружающая следующую страницу.
- **Секция очереди**: фоновые операции сверху, задания снизу.
- **Панель массовых действий**, **плеер-бар**, диалоги плеера, лога и ID3-тегов, тост.

### 5.3 Обновление данных

| Событие | Источник | Реакция |
|---|---|---|
| `mediaRefresh` | SSE-тема `library`, `HX-Trigger` | перезапрос `library/items` |
| `queueRefresh` | SSE-тема `queue`, `HX-Trigger` | перезапрос `queue/items` |
| `tagsRefresh` | SSE-тема `tags`, `HX-Trigger`, смена фильтра | перезапрос `library/tags` |
| `collectionsRefresh` | SSE-тема `collections`, `HX-Trigger` | перезагрузка сайдбара |
| `showToast` | `HX-Trigger` | всплывающее уведомление |

Фильтр хранится в JS-объекте `{q, kind, tag}` и зеркалится в скрытую форму
`#filter-form`, которую HTMX включает в каждый запрос фрагментов. Фильтрация
и пагинация — полностью серверные.

### 5.4 Плеер

Единый контроллер видео и аудио: одновременно играет только один. Видео — в
`<dialog>` с Plyr, Escape и клик по подложке сворачивают в бар. «Воспроизвести
всё» тянет плейлист с сервера по текущему фильтру (без ограничения страницей).
Бар: название, прогресс с перемоткой, play/pause, стоп, развернуть.

**Телефон в горизонтальной ориентации.** Окно плеера разворачивается на весь
экран, видео вписывается по высоте (Plyr держит собственную обёртку с фиксированной
пропорцией, поэтому ограничение задаётся и ей). Телефон определяется низким экраном
вместе с сенсорным вводом:
`(orientation: landscape) and (max-height: 600px) and (pointer: coarse)`. Одних
размеров мало — под них попадает и небольшое окно браузера на десктопе (headless-окно,
например, 780×437). Высота считается в `dvh`: `vh` в мобильном Safari не учитывает
динамические панели.

**Полноэкранный режим на iOS** отдаётся нативному плееру (`iosNative`): Safari не
поддерживает Fullscreen API для произвольных элементов, и запасной режим Plyr там
упирается в размеры окна.

### 5.5 Страница настроек

Параметры загрузчика (форма перекрытий с placeholder из env), импорт
`cookies.txt` в формате Netscape с разбором по доменам, кнопки «Пересчитать»
(reindex) и «Очистить» (cleanup) — обе ставят фоновую операцию. «Пересчитать»
чистит оборванные привязки и пустые теги, но коллекции не удаляет: пустая
подборка — пользовательская сущность, а не мусор.

## 6. Поведенческие правила

- **Soft delete**: файл стирается с диска, запись с URL и именем остаётся;
  доступна через `GET /items/deleted`.
- **Скрытие** убирает задание из медиатеки без потери данных; безвозвратное
  удаление доступно только для скрытых.
- **Повторы** экспоненциальные до `RETRY_MAX_DURATION`, затем `failed` с ручным сбросом.
- **Отображение имени**: имя файла (очищенное от артефактов yt-dlp) → заголовок
  задания → усечённый URL.
- **Плейлист** = N независимых заданий с общим тегом.
- **Гонка сканера и загрузчика** исключена staging-каталогом и множеством `InFlightPaths`.
- **Куки** хранятся по доменам и материализуются в `<output>/.talmor-cookies.txt` (0600).
- **Файл, вернувшийся на диск**, снова становится доступным: пометки об удалении
  и пропаже снимаются.

## 7. Тестирование

Юнит-тесты покрывают: пулы и прагмы БД, репозитории (включая пагинацию, поиск по
тегам, защиту от удаления нескрытого задания, восстановление доступности файла),
провайдер настроек, сервисы медиатеки и очереди (удаление, постоянные ссылки,
массовая отмена с остановкой загрузок, redownload, восстановление `checking`),
исполнитель операций (полосы, восстановление после рестарта), сборку аргументов
yt-dlp, очистку имён, сканер каталога, валидацию переименования.

e2e (`tests/e2e`, chromedp) компилируются и берут браузер из `CHROME_PATH`;
в CI пока исключены. Не покрыты `worker.Pool`, бот и HTTP-обработчики — см. TODO.

## 8. Развёртывание

Multi-stage Dockerfile: сборка `CGO_ENABLED=0` → alpine с `ffmpeg`, `python3` и
`yt-dlp` из pip (`/usr/bin/yt-dlp`). Том `/data` хранит БД, медиатеку, staging и куки.
Для k8s: 1 реплика, PVC на `/data`, Ingress + `BASE_PATH`, ConfigMap/Secret для env.
